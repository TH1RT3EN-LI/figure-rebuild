# 绘制过程录制

此流程由调用方在支持浏览器录屏的环境中执行，不是 `run.py` 的内置录制命令。适用于用户要求展示图形逐步复建的过程。使用当前环境提供的浏览器控制接口，先读其录制能力文档；不可绕过该环境的 UI 操作规则。

## 实际绘制与来源

1. 先核对原图、字体和公式，按可见关系组织对象。将原图和重绘画布并排或上下展示。
2. 每次实际插入一批对象后，原子写入累计清单、预览及状态。事件日志记录稳定对象 ID、revision、墙钟时间和预览 SHA256。状态使用递增序号；不能只播放预先导出的完整图来冒充绘制过程。
3. 页面明确标记“程序绘制过程”或真实使用的编辑器。照片、热图和公式资产的来源与可编辑性沿用清单，不把 LaTeX 图版计作原生文字。
4. 录制画布只是创建过程的证据。完成清单仍须 review、build，再核对实际导出 PPT，尤其检查旋转文字、字体行高、遮挡和全部连接。

## 浏览器帧采集

- 录制前确认本地预览服务器仍能响应、页面确实刷新。辅助服务器保持低噪声日志；定期验证存活，不能依赖已缓存的参考图判断服务正常。
- 若环境提供 CDP screencast，保存每帧原始 PNG、浏览器时间戳和采集日志，并及时确认该帧。未确认的首帧会阻止后续绘制帧，不能等绘制已开始才建立采集循环。
- 先运行采集，再开始绘制。跨工具启动时可给作者进程留明确的准备时间，保证采集循环已开始；交付视频可裁掉这段空闲等待。
- 需要持续调用工具的循环应在有效的调用上下文中被等待。不要让未等待的后台 Promise 跨工具调用继续使用接口；这可能导致上下文已失效。按环境限制分段采集，保持同一事件游标并避免截断；将状态保存在可持续访问的对象中。
- 保持当前浏览器尺寸。记录帧尺寸，遇到用户窗口变动先检查编码兼容性；不要为了截图美观修改浏览器 viewport。

## 编码与验收

按浏览器捕获时间差生成每帧持续时间，再编码 MP4。保持绘制阶段的速度；只裁空闲开头或结尾，并在审计中记录裁剪边界。输出固定帧率时的补帧不能被称为额外的原始捕获帧。

用事件日志对照捕获时间，确认每个插入阶段都有录制画面。时间覆盖只是诊断，还应从最终视频提取开头、中段和完成帧，亲自核对画布确实逐渐增加对象。用户只要画布时，按其实际显示区域裁掉界面文字、参考图和面板框，再抽帧核对边缘没有切掉图内标注或轮廓。检查可解码性、时长、尺寸与最终画面；只有空白和成图两帧的录像不足以证明绘制过程。

## README 动图

用户要求 README 动图时，从已验收的纯画布视频生成 GIF，裁掉空闲等待，生成统一调色板并压缩重复区域。适度加速需保持步骤可辨，播放倍率记录在素材元数据中；用户要求简洁标题时，首页无需展示倍率。检查尺寸、帧数、总时长、循环设置及中段和最终帧；使用仓库内相对资产路径。论文案例应标注原论文，且同步更新关于自建素材与第三方图像的说明。

用户需要对比时，将注明来源的原图放在动图旁或上方，保持相同显示宽度。README 首页优先保留用途、效果、编辑边界、最短安装与使用方式；详细协议和诊断流程放在使用指南。开发与测试所用智能体不等于工具的使用限制；独立 CLI 与特定智能体的 skill 安装应分开描述，同时保留真实的后端依赖。多语言版本共用技术事实、安装命令、徽章和素材，在顶部提供语言选择。翻译完成后重新核对当前包入口与各语言代码块，避免安装方式在并行修改中发生偏差；本地渲染页面的语言链接应切到对应预览，而不是打开 Markdown 源码。

需要检查 GitHub 风格渲染时，可将 README 经 GitHub Markdown API 的 `gfm` 模式渲染，再在本地配合 GitHub Markdown 样式展示。保留本地素材的相对路径；API 返回的标题若无 ID，应补上兼容的标题锚点。使用指向仓库根目录的 `base` 时，同页导航必须显式指向预览页面，避免 `#标题` 跳到服务器根目录。亲自确认图片加载与 GIF 播放，留下可打开的本地预览和截图；不要把本地预览描述成已发布的 GitHub 页面。
